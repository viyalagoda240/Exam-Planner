1. What is an embedded system?

Definition. An embedded system is a combination of computer hardware and software, designed to perform a specific, dedicated function within a larger mechanical or electrical system. It usually runs a fixed program (firmware) and interacts with the physical world through sensors and actuators.

Examples: washing machine controller, microwave oven, digital watch, car airbag controller, pacemaker, traffic light controller, smart meter.

Key characteristics (how it differs from a general-purpose computer)

  1. Dedicated function. It does one job (or a small set of jobs) for its whole life. A PC runs any program the user installs.
  2. Real-time operation. It must react within a fixed time limit (an airbag must fire within milliseconds).
  3. Resource-constrained. Small memory (KB, not GB), slow CPU (MHz), limited power and low cost.
  4. Reactive and connected to the physical world. It reads sensors and drives actuators continuously.
  5. High reliability and stability. It must run for months or years without restarting, often with no human watching.
  6. Low power consumption. Many run on batteries, so they sleep whenever possible.
  7. Fixed firmware. The program is stored in ROM/Flash; the user normally cannot change it.
  8. Small size, little or no user interface (a few buttons, LEDs or a small display).

Microcontroller vs microprocessor

Microcontroller (MCU): a single chip that contains a CPU plus RAM, ROM/Flash, I/O ports, timers, ADC and serial interfaces. It is a complete small computer for a dedicated task. Examples: ATmega328P (Arduino Uno), PIC16F877A, 8051, ESP32.

Microprocessor (MPU): a chip that contains only the CPU. RAM, storage and I/O must be added as separate chips. It is built for high processing power. Examples: Intel Core i5, AMD Ryzen, ARM Cortex-A in phones.

3. Requirements and real-time systems

Functional vs non-functional requirements

Functional requirements say what the system must do – its functions and behaviour.

Non-functional requirements say how well it must do it – quality limits such as response time, power, cost, size, reliability, accuracy and security.

Example: a smart home temperature monitor

  • Functional: read the room temperature every 5 seconds; switch the fan on when the temperature is above 30 °C; show the temperature on an LCD; send an alert to the phone if it is above 35 °C.
  • Non-functional: respond within 1 second; accuracy ±0.5 °C; run 24/7 without failure; battery lasts at least 6 months; cost below Rs. 5,000.

Hard vs soft real-time systems

A real-time system must produce the correct result within a deadline. A late answer is a wrong answer.

Hard real-time: missing a deadline causes system failure, damage or danger to life. Examples: airbag controller, ABS braking, pacemaker, aircraft flight control.

Soft real-time: missing a deadline only reduces quality; the system keeps working. Examples: video streaming (a frame is dropped), online games, music players, a smart TV menu.

PointHard real-timeSoft real-time
Deadline missNot allowed – failureAllowed sometimes – lower quality
DesignWorst-case timing must be guaranteedAverage performance is enough
ExampleAirbag must fire within about 30 msVideo call can skip a frame

සිංහලෙන්: Functional = system එක කරන්න ඕනේ වැඩ (temperature කියවන්න, fan එක on කරන්න). Non-functional = ඒ වැඩේ කොච්චර හොඳට කරන්න ඕනෙද (තත්පර 1කින් response, battery මාස 6ක්, මිල අඩු).

4. Hardware components of an embedded system

Microcontroller
The brain. Runs the program, reads inputs, takes decisions and controls the outputs.
Memory (RAM & ROM)
Flash/ROM (program memory) stores the firmware permanently – it is non-volatile. RAM/SRAM (data memory) holds variables and the stack while running – it is volatile. EEPROM stores small settings that must survive power loss (e.g. calibration values).
I/O interfaces
Connect the MCU to the outside world: digital GPIO pins, ADC (converts an analog sensor voltage into a number), PWM (controls motor speed or LED brightness), communication ports.
Sensors
Convert a physical quantity into an electrical signal. Examples: LM35 / DHT11 temperature, LDR light, HC-SR04 ultrasonic distance, PIR motion, soil moisture, MQ-2 gas.
Actuators
Convert an electrical signal into physical action. Examples: DC/servo/stepper motors, relays, LEDs, buzzers, solenoid valves, displays.
Communication modules
Exchange data with other chips or systems: UART, SPI, I2C (wired, on the board); Wi-Fi, Bluetooth, GSM, LoRa, Zigbee (wireless).
Power management unit
Regulates the voltage, manages the battery or solar charging, switches the MCU into sleep modes and protects against low voltage (brown-out). Gives long battery life and stable operation.

සිංහලෙන්: Sensor = ලෝකයේ දෙයක් (උෂ්ණත්වය, එළිය, දුර) electrical signal එකක් කරනවා. Microcontroller = ඒ signal එක කියවලා තීරණය ගන්නවා. Actuator = තීරණය අනුව වැඩක් කරනවා (motor එක කරකවනවා, LED එක පත්තු කරනවා). Flash එකේ program එක ස්ථිරව තියෙනවා; RAM එකේ run වෙන වෙලාවේ variables තියෙනවා (current ගියාම මැකෙනවා). Power unit එක battery එක ඉතුරු කරනවා.

5. Communication: synchronous vs asynchronous, UART, SPI, I2C

Synchronous communication: the sender and receiver share a common clock signal. Each bit is read on a clock edge, so no start/stop bits are needed and it can be fast. Needs an extra clock wire. Examples: SPI, I2C.

Asynchronous communication: there is no shared clock. Both sides agree on a speed (baud rate, e.g. 9600 bps) and every byte is wrapped with a start bit and stop bit(s), sometimes a parity bit. Example: UART – an Arduino talking to a PC, a GPS module or a Bluetooth HC-05 module.

UART frame (one byte): line idle = 1 → start bit 0 → 8 data bits (LSB first) → optional parity → stop bit 1. Wires: TX, RX, GND. Point-to-point, full duplex.

UART = async. SPI, I2C = sync.

6. Polling, interrupt-driven I/O and ISRs

Polling: the CPU repeatedly checks (in a loop) whether a device needs service, e.g. "is the button pressed?" again and again. Simple to write, but it wastes CPU time and power, and a very short event can be missed or handled late.

Interrupt-driven I/O: the device sends an interrupt signal to the CPU only when it needs attention. The CPU pauses the main program, runs a special function (the ISR), and then continues where it stopped. The CPU is free (or asleep) the rest of the time, and the response is fast.

A scenario where interrupts are preferred

An emergency-stop button on a factory machine: the motor must stop immediately, even if the main program is busy. With polling, the button might be checked too late. With an external interrupt (INT0), the CPU jumps to the stop routine within microseconds.

Other good scenarios: a battery-powered sensor node that sleeps until a PIR motion sensor wakes it; receiving serial data (UART RX interrupt) so no byte is lost; counting fast pulses from a wheel encoder; an airbag crash sensor.

Interrupt Service Routine (ISR)

An ISR is a special function that the processor runs automatically when a specific interrupt occurs. It handles the event and then returns control to the interrupted program.

Purpose: respond quickly to time-critical events; handle hardware events such as a timer overflow, a button press or received data; let the CPU do other work (or sleep) instead of waiting; save power.

What happens when an interrupt occurs:

  1. The device sets its interrupt flag.
  2. The CPU finishes the current instruction.
  3. It saves the return address (program counter) on the stack and disables further interrupts.
  4. It jumps to the ISR address found in the interrupt vector table.
  5. The ISR runs.
  6. The RETI instruction restores the program counter, re-enables interrupts and the main program continues.

Rules for a good ISR: keep it short; no delays or long loops inside; use volatile variables to share data with the main program; clear the flag if the hardware does not.

// ATmega328P: toggle an LED on PB0 when a button on INT0 (PD2) is pressed
#include <avr/io.h>
#include <avr/interrupt.h>

ISR(INT0_vect) {            // runs automatically on the interrupt
    PORTB ^= (1 << PB0);    // toggle LED
}

int main(void) {
    DDRB  |= (1 << PB0);    // LED pin = output
    PORTD |= (1 << PD2);    // pull-up on the button pin
    EICRA |= (1 << ISC01);  // interrupt on falling edge (button press)
    EIMSK |= (1 << INT0);   // enable INT0
    sei();                  // enable global interrupts
    while (1) { }           // main program is free to do other work
}

සිංහලෙන්: Polling කියන්නේ CPU එක නැවත නැවත "button එක press කළාද? press කළාද?" කියලා අහන එක – මහන්සියි, current නාස්තියි. Interrupt කියන්නේ button එකම "මට දැන් උදව් ඕනේ" කියලා CPU එකට කියන එක. එතකොට CPU එක කරමින් හිටපු වැඩේ නවත්තලා ISR එක run කරනවා, ඊට පස්සේ ආයෙත් කලින් වැඩේට යනවා. ISR එක කෙටි වෙන්න ඕනේ.

7. Embedded C: functions, port registers, LED + button

Why functions are useful in embedded C

  1. Modularity: a big program is split into small tasks (readSensor(), updateDisplay()).
  2. Reusability: write once, call many times (delay_ms(500) used everywhere).
  3. Smaller code size: no repeated code, so less Flash memory is used – important on small MCUs.
  4. Readability and maintenance: led_on() is easier to understand than a bit operation.
  5. Easier testing and debugging: each function can be tested alone.
  6. Hides hardware details: if the LED moves to another pin, only one function changes.
void led_on(void)  { PORTB |=  (1 << PB0); }   // set bit = LED ON
void led_off(void) { PORTB &= ~(1 << PB0); }   // clear bit = LED OFF
uint8_t button_pressed(void) {                  // button to GND, pull-up on
    return !(PIND & (1 << PD2));               // pressed reads 0
}

Turn ON an LED when a button is pressed

Assumptions (always write them): LED on PB0 with a resistor (active high). Push button between PD2 and GND, internal pull-up enabled, so pressed = 0.

#include <avr/io.h>

int main(void) {
    DDRB  |=  (1 << PB0);      // PB0 output (LED)
    DDRD  &= ~(1 << PD2);      // PD2 input (button)
    PORTD |=  (1 << PD2);      // enable pull-up

    while (1) {
        if (!(PIND & (1 << PD2)))     // button pressed (reads 0)
            PORTB |=  (1 << PB0);     // LED ON
        else
            PORTB &= ~(1 << PB0);     // LED OFF
    }
}

  LOOP forever

     IF button is pressed THEN LED = ON
     ELSE LED = OFF

8. Hardware timers and a 1-second delay

A hardware timer is a counter register inside the microcontroller that counts clock pulses independently of the CPU. The clock first passes through a prescaler (÷1, ÷8, ÷64, ÷256, ÷1024), then the counter register (TCNT0) increases by one on every tick.

An 8-bit timer counts 0 → 255. On the next tick it overflows back to 0 and sets the overflow flag, which can trigger an interrupt. In CTC mode (Clear Timer on Compare) the counter is compared with OCR0A; when they are equal the counter resets to 0 and a compare-match interrupt can run.

Delay generation: because the tick time is fixed, counting a known number of ticks gives an exact time. The CPU can either wait for the flag (polling) or keep working and let the timer interrupt count the time.

Tick time = prescaler ÷ clock frequency

Overflow time (8-bit) = 256 × tick time

Worked example: 1-second delay, 8-bit timer, 1 MHz clock (2025 Q5(b))

PrescalerTick timeOverflow time (256 ticks)Overflows in 1 s
11 µs0.256 ms3906.25
88 µs2.048 ms488.28
6464 µs16.384 ms61.04
10241.024 ms262.144 ms3.81

Exact method (CTC): prescaler 8 → tick = 8 ÷ 1 MHz = 8 µs. For 1 ms we need 1 ms ÷ 8 µs = 125 ticks, so set OCR0A = 124 (counts 0…124). The compare interrupt now runs every 1 ms. Count 1000 interrupts = exactly 1.000 s.

Simple overflow method: prescaler 64 → overflow every 16.384 ms. 1 s ÷ 16.384 ms = 61.04, so count 61 overflows ≈ 0.9994 s (0.06 % error).

// ATmega328P, 1 MHz clock: toggle an LED on PB5 every 1 second
#include <avr/io.h>
#include <avr/interrupt.h>

volatile uint16_t ms = 0;

ISR(TIMER0_COMPA_vect) {          // runs every 1 ms
    ms++;
    if (ms >= 1000) {             // 1000 ms = 1 s
        ms = 0;
        PORTB ^= (1 << PB5);      // 1-second event
    }
}

int main(void) {
    DDRB  |= (1 << PB5);          // LED output
    TCCR0A = (1 << WGM01);        // CTC mode
    OCR0A  = 124;                 // 125 ticks x 8 us = 1 ms
    TIMSK0 = (1 << OCIE0A);       // enable compare-match interrupt
    TCCR0B = (1 << CS01);         // prescaler 8 -> timer starts
    sei();                        // global interrupts on
    while (1) { }                 // CPU free for other work
}

Pseudocode / flow (enough for full marks if you explain the numbers):

MAIN: set LED pin output
      set timer: prescaler 8, CTC mode, compare value 124
      enable compare interrupt, enable global interrupts
      LOOP forever (do other work)

ISR (every 1 ms): count = count + 1
      IF count = 1000 THEN  toggle LED (1 second passed), count = 0
      RETURN

Register names are for the ATmega328P (Arduino Uno). Other AVR chips use slightly different names (e.g. ATmega32 uses TCCR0, TIMSK); the idea is the same.

  • AVR is an 8-bit RISC microcontroller with 32 general-purpose registers, R0–R31. LDI works only with R16–R31.
  • Most instructions take 1 clock cycle. It uses a Harvard architecture (separate program and data memory).

2026 Q3(a): final value of r16

ldi r16, 0x05    ; r16 = 5
ldi r17, 0x03    ; r17 = 3
sub r16, r17     ; r16 = 5 - 3

r16 = 0x02 (binary 0000 0010).

SUB can change the flags H, S, V, N, Z, C. Here: Z = 0 (result is not zero), C = 0 (5 ≥ 3, no borrow), N = 0 (bit 7 is 0), V = 0 (no signed overflow), S = N ⊕ V = 0, H = 0 (low nibble 5 ≥ 3, no borrow from bit 4). LDI does not change any flag.

2026 Q3(b): what does this loop do?

      ldi  r18, 0x03   ; counter = 3
Loop: dec  r18         ; counter = counter - 1
      brne Loop        ; repeat while counter != 0 (Z = 0)

It is a count-down loop that runs 3 times and is used as a short software delay.

  • Pass 1: r18 = 3 → 2, Z = 0 → branch back.
  • Pass 2: r18 = 2 → 1, Z = 0 → branch back.
  • Pass 3: r18 = 1 → 0, Z = 1 → BRNE does not branch; the program continues with the next instruction.

DEC changes S, V, N, Z (not C). Time: LDI 1 cycle + 3 × DEC (1) + 2 taken BRNE (2 each) + 1 not-taken BRNE (1) = 9 cycles = 9 µs at 1 MHz. A bigger starting value gives a longer delay.

10. Microcontroller architecture and the fetch–decode–execute cycle

CPU
ALU does arithmetic and logic; the control unit decodes instructions and sends control signals; registers hold the data being worked on. The program counter (PC) holds the address of the next instruction; SREG holds the flags.
Program memory (Flash)
Stores the program instructions; non-volatile.
Data memory (SRAM)
Stores variables and the stack while the program runs; volatile.
I/O ports
Connect pins to the outside: inputs (switches, sensors) and outputs (LEDs, motors).

Fetch–decode–execute

  1. Fetch: the CPU reads the instruction at the address in the PC from program memory into the instruction register; the PC increases to point to the next instruction.
  2. Decode: the control unit works out the operation (opcode) and the operands (which registers or constant).
  3. Execute: the ALU performs the operation, the result is written back to a register or memory, and the flags in SREG are updated.

Example: ADD R16, R17 with R16 = 5 and R17 = 3. Fetch: the instruction is read from Flash at address PC; PC = PC + 1. Decode: "ADD, destination R16, source R17". Execute: the ALU adds 5 + 3 = 8, writes 8 into R16, sets Z = 0, C = 0, N = 0.

AVR overlaps these steps (a 2-stage pipeline): while one instruction executes, the next is being fetched, so most instructions finish in one clock cycle.

Data flow: input port → CPU → output port (2026 Q5(b))

  1. Read from an input port: IN R16, PIND – the switch level on the pin is copied over the data bus into register R16.
  2. Processed by the CPU: e.g. ANDI R16, 0x01 or a compare – the ALU tests the bit; the control unit decides what to do next (branch).
  3. Sent to an output port: OUT PORTB, R16 – the register value travels over the data bus to the PORTB latch and appears on the pins, switching the LED on.

B. Smart street lighting (2026 Q2)

  • Sensors: LDR (ambient light level, read through the ADC); PIR motion sensor (people or vehicles nearby). Optional real-time clock (RTC).
  • Actuators: LED street lamp driven by PWM through a MOSFET driver (brightness control); relay for an AC lamp.

LOOP
   light = read LDR (ADC)
   IF light > DAY_LEVEL THEN           lamp OFF            (daytime)

   ELSE                                lamp 30 %           (night, no traffic)
   use two thresholds (hysteresis) so the lamp does not flicker at dusk
END LOOP

Two improvements (evaluate = say the benefit and any cost):

  1. Motion-based dimming (PIR + PWM): bright only when needed – saves about 40–60 % energy and extends LED life; small extra cost for the sensor.
  2. Solar panel + battery: works during power cuts and needs no grid cable – very reliable; higher installation cost.
  3. Fault reporting over GSM/LoRa: the lamp reports when it fails, so repairs are faster – improves reliability.

C. Smart home temperature monitoring (2026 Q1(c))

  • Inputs: temperature sensor (DHT22 / LM35), humidity sensor, user set-point buttons or phone app.
